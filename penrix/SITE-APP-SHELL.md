# Penrix Site-App Shell — 私人浏览器的真实产品形态（Working）

> **设计与验收优先接口：** [PRODUCT-DESIGN-STANDARD-Working.md](PRODUCT-DESIGN-STANDARD-Working.md)。本文回答**为什么做站点 App 化、内容与边界是什么**；新文档回答**最终长什么样、对标什么、哪些行为才算完成**。开发和 Codex 执行必须两者同时引用。

> **作者最新指令，2026-11-04：** “我有官方的Firefox ，你这个版本只做私人浏览器，深度定制我要求的几个网站。做到极致优化，懂我的意思吗？就像是这几个网站的app一样。那种定制的感觉。打开私人浏览器打开这几个网站就跟app里几个模块一样。”
>
> 这是产品定义的**第一优先级**，高于此前“保留一个通用 Firefox，再加少量小说功能”的表达。不是要求把 Firefox 官方浏览器换个图标，不是网址导航页，也不是给网页套一个没有地址栏的壳。

## 一、目标界面：一个私人 App，若干网站专属模块

真正交付对象是 **Penrix Private / 专用站点超级应用**，底层运行 Firefox Fenix + GeckoView，但表面应像用户熟悉的几个 App 模块：

```text
                  打开 Penrix Private
                         |
                         v
               【私人模块主界面】
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
      小说站模块       论坛站模块      漫画/视频站模块
          |              |              |
      站点自己的首页   站点自己的帖子   站点自己的媒体
      搜索/作品/目录   分类/帖子/收藏   分类/详情/播放
      原生阅读/书架    优化回帖与阅读   图册/全屏/收藏
          |              |              |
          +--------------+--------------+
                         |
                  【专用任务模块】
                         |
                         v
               保留手机 AutoJs6 协作
```

这里“站点模块”指一站或一组**明确指定**的相关网站对应的独立体验；不能把所有网站笼统堆入同一“小说模块”，更不能假定旧 SiteRegistry 里出现过的站点都已获得作者本轮逐站定制授权。

### 和现在的旧主页的本质区别

旧 `MainActivity.siteTile()` 的实际行为是 `setOnClickListener { openUrl(site.startUrl) }`：**点图标→用普通浏览器打开网址**。这只是快捷入口。

新方案应当是：

```text
点击某站模块
    |
    v
恢复该站上次状态（当前页/筛选/滚动/阅读位置）
    |
    v
站点专属界面
    +-- 站点识别与专属导航
    +-- 专属搜索/分类/列表
    +-- 站点当前页面识别：首页/列表/详情/正文/登录/播放器...
    +-- 按现场给出专属按钮，而不是浏览器通用工具栏
    +-- 广告和多余页面元素净化
    +-- 浏览器引擎继续执行真实网站登录/脚本/请求
    |
    +-- 需要原站完整交互？→ 一键切回原网页，不丢当前状态
    |
    +-- 切到另一个模块 → 保留原模块状态
```

“像 App”是**操作流与状态结构**，不是仅仅隐藏地址栏、美化图标或默认全屏。单个模块内连贯完成典型任务，尽量不让作者意识到正在“不断打开网页”。

## 二、每个模块怎样专属优化（先按旧仓库已有站点分类作候选，具体名单以作者确认为准）

原项目 `SiteRegistry.kt` 当前存在小说、论坛、漫画、视频、导航五类网站，以下是**实现方式示例**，不是宣布全部这些站点第一轮就开发。

| 示例站点（旧仓库已有入口） | 它应像哪种 App | 必须优化的典型操作 | 专属处理重点 |
|---|---|---|---|
| TWKAN、69书吧、UU看书、八叉书库 | 小说/阅读 App | 进入→搜书→作品→目录→正文→下一章→书架与进度 | 统一作品与章节身份、正文清洗、阅读页面、跨来源连续阅读 |
| SIS001、Cool18 | 论坛 App | 分类→帖子列表→阅读→收藏/返回原列表位置 | 论坛帖子主内容净化、分页/楼层、登录、图文与回退位置；发帖保持真实网站 |
| WNACG、18Comic、漫画柜 | 漫画 App | 分类/作品→图集→整组图片连续浏览→回作品 | 图片顺序、懒加载、缩放、翻页与长图浏览、阅读进度 |
| Iwara、Hanime1 等 | 视频 App | 分类/搜索→视频→全屏→返回列表与继续观看 | 真播放器不重写、全屏/媒体按钮、播放恢复与网页广告清理 |
| 特定导航网站 | 分类入口 App | 分类→链接→在对应模块/原网页打开 | 去噪、统一可返回路径、不破坏外链 |
| Epic / 任务入口（若仍保留） | 专用任务工具 | 打开任务页→保留会话→AutoJs6 交互→核对真实结果 | 不自动重新实现领取；原有手机端脚本继续为执行者 |

**不做一套假通用的“所有网站模板”**。底层只复用稳定的站点识别、导航桥、数据储存和恢复机制；每个重点网站单独设计自己的用户旅程与特殊动作。

## 三、用“网页运行 + 原生体验”的双层结构实现，而不是直接替换整个网站

```text
【网站真实运行层：GeckoView】
  - 真实网址、登录会话、请求、JS、图片/视频
  - 官方 Firefox/站点权限、标准 Web 能力
          |
【站点适配层：Penrix 内置 WebExtension + Native Messaging】
  - 识别域名与当前页面类型
  - 检测页面关键对象：作品/目录/章节/帖子/图集/视频
  - 清除广告与干扰，提取需要的内容与行动入口
  - 监听页面 SPA 切换、分页、登录与新窗口
  - 失败→原始网页，而不是白屏或假数据
          |
【模块交互层：Android 原生界面】
  - 各站自己的首页/搜索/分类/操作栏/继续上次操作
  - Reader、图片阅读器、收藏、书架、阅读进度
  - 最近使用/模块切换/回到站点
          |
【本地数据层】
  - 每站独立导航/会话入口状态、专属设置
  - 跨站统一作品书架与阅读进度（有稳定 ID）
  - 当前浏览器 Session/Cookie 由 GeckoView 管，不重复持有伪造会话
```

**具体场景一：小说站。** 进入 TWKAN 模块不是看到 TWKAN 网页加 Firefox 地址栏，而是看到该站的内容入口/分类/最近在读。选择作品后页面操作转为「目录、阅读、加入书架」，正文阅读调用 PenrixReader，下一章沿原有 Source 取章流程。需要网站验证时回原站并在通过后继续。

**具体场景二：论坛。** 点击某论坛模块，显示“分类/帖子/收藏”，帖子详情可以保留原网页交互、登录和回复能力，但去掉不需要的横幅、重复导航与干扰；退出帖子返回之前列表和滚动位置，而不是每次从论坛首页重新打开。

**具体场景三：漫画/视频。** 保留网站自身的媒体权限与资源获取机制，针对展示体验优化原生全屏、观看/阅读进度、返回原列表、页面净化。不要为表面上“原生”而重造视频解码器、破解付费权限或绕过站点登录。

## 四、区别于普通浏览器的关键验收

| 普通网址壳的表象 | 真正的站点 App 模块 |
|---|---|
| 打开网站首页 | 恢复上次列表/作品/帖子/播放页面 |
| 到处都是网站旧导航 | 按站点内容结构提供适合手机的专属导航 |
| 只有书签 | 知道当前是什么书、章节/帖子/图集以及关联状态 |
| 所有站共用同一工具栏 | 阅读、帖子、图片、视频分别显示有意义的操作 |
| 链接每次重新开浏览器页 | 模块内部路由、跨模块切换和返回关系连贯 |
| 随机 CSS 去广告 | 针对实际页面识别后清理，不误删正文/按钮/播放器 |
| 出错则空白或无限重试 | 明确保留一键查看完整原网页，能返回原操作 |
| 只验证主页能打开 | 验证一条完整任务：搜索→详情→内容→返回/下次接续 |

## 五、模块化交互与状态，不是简单堆 Tab

```text
打开 App
  |
  v
【私人首页】
  |
  +-- 进入站 A ---→ A 的首页/上次位置
  |                     |
  |                     +→ A1 列表/分类
  |                     +→ A2 内容详情
  |                     +→ A3 阅读/播放
  |                     +→ A4 站点设置
  |                     |
  |                     +→ 切换站 B → B 上次位置
  |                                          |
  |                                          +→ 返回站 A → A2/A3
  |
  +-- 进入站 C ---→ C 的首页/上次位置
  |
  +-- 站点外链接 → 受控“普通网页”作为辅助视图
  |
  +-- 出错/站点改版 → 原网站完整模式 → 再进入专用模块
```

采用**每站独立的模块路由状态**，而不是为每个站复制整个浏览器进程。是否需要每站独立 Cookie/Profile 要先看真实登录和数据隔离要求，不能擅自引入有损会话兼容的多 Profile 方案。

主首页应当成为私人 App 的模块总入口，而不是 Firefox 默认资讯/推荐/搜索首页；一般网页能力保留作异常和外链兜底，但**不作为产品主界面**。

## 六、开发顺序的改变

原文档 `PRODUCT-REQUIREMENTS.md` 的 F0–F5 是技术执行阶段，这里以新的产品形态重新设定其目标：

1. **F0 — 独立 Penrix Firefox APK（可与官方 Firefox 和旧 Penrix WebView 并存）**。K20 Android 9 安装；确认官方 Firefox 的设置、数据、默认浏览器均未被覆盖。
2. **F0.5 — 私人 App 外壳**。进入 APP 立即看到模块首页；点击至少一个真实站点进入专属模块；模块内返回、切换、恢复上次位置、原网页模式可以工作。不把“快捷入口网址格子”当通过。
3. **F1 — 第一个站点深度闭环**。建议优先从真实证据最多的小说站开始（如 TWKAN/69书吧），用一个站实现搜索→作品→目录→原生阅读→下一章→书架进度→回站点，再抽出稳定的模块基础。**不是先铺满所有站点图标。**
4. **F2 — 扩展作者真正要求的其他重点站点**。论坛/漫画/视频逐站做页面识别、专属导航和完整操作闭环；不同网站允许不同界面，不套统一网页卡片模板。
5. **F3 — 体验优化**。uBlock Origin + 每站定制清理；页面加载与返回状态、沉浸阅读、媒体全屏、字体、离线缓存、重要动作布局和 Android 9 性能优化。先解决使用障碍再做装饰。
6. **F4 — 既有任务自动化适配**。保留旧 AutoJs6 工作流，在新 App 中重新验证真实页面与会话，再决定迁移。
7. **F5 — 自研扩展、数据备份等加分项**。

**验收基准不是 Firefox 正常浏览一个网页，而是作者在某个站点里能否像使用那个站的专属 App 一样完成连续任务，并且重复使用。**

## 七、必须保留的边界

- 作者已有**官方 Firefox**；Penrix 只做**私人专用浏览器**，不替代、不改造、不覆盖官方 Firefox 的安装、会话、浏览历史和设置。
- 不把隐私加固当产品第一主题；实用的专属体验更重要，基础安全与内容/会话保护不能因此退化。
- 不把 Chrome 扩展能力当硬门槛；它是加分项。Firefox 自带可安装完整版 uBlock Origin。
- 不为项目工程规模牺牲用户真实功能；是否采用官方 Fenix 的某项组件，以产出的实际站点体验为准。
- 不自动认定 SiteRegistry 旧名单的每个站都必须深度开发：优先集合应从作者已经明确要求和旧真实使用证据中确认，随真实验证扩充。
- 新版不覆盖原 Penrix WebView 与官方 Firefox；旧本地有未提交修改，要保护，数据导入需可恢复。
- 本文是**需求定位与设计**，不代表已经写好/编译过 Firefox 定制 APK。
